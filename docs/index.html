Stand-ins for the outside world.

Every project that talks to a payment gateway, an identity check, an email provider, a DNS provider, a messaging service or a model API needs something to talk to in a test. This is that something — one implementation, shared, instead of a copy in every repository.

Using it

In a test

import { startMock } from '@bytesickle/api-mock-services'

const stripe = await startMock('stripe')

process.env.NUXT_STRIPE_API_BASE = `${stripe.url}/v1`

// ... the test ...

expect(stripe.last().path).toBe('/v1/refunds')
await stripe.close()

As a container

docker run --rm -p 4001:4001 api-mock-services stripe

# one image, one process, as many mocks as you like
docker run --rm -p 4001:4001 -p 4005:4005 api-mock-services stripe paystack

As a whole stack

docker compose -f examples/docker-compose.yml --profile payments up -d
docker compose -f examples/docker-compose.yml --profile identity up -d
docker compose -f examples/docker-compose.yml --profile all up -d

From another language

The mocks answer over HTTP, so anything can use them. Point the application at the URL and carry on — there is nothing to install.

Design

The engine and the browser are two things, and they do not mix. src/harness.js records requests, keeps state and answers over a control surface. Everything a person sees lives in src/ui/, with the markup in templates/ and the styles in assets/.

No dependencies

Node's own HTTP server. The lint, the tests and the footprint budget are all written with what node already has.

Real shapes

The paths, the fields and the status codes are the provider's, so the code under test does not change when it is pointed at a mock.

The state is kept

What the service was asked, and what it decided, is on service.state and service.requests.

The reference decides

A reference with success in it comes back successful, one with failed in it comes back failed.
