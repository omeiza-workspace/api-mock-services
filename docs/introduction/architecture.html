Documentation / Introduction

How it is built.

One implementation, no dependencies, and a promise that is checked. The short version is all of it. The rest of this page is why each piece is the way it is.

The shape

src/
  harness.js     the engine — routes, state, the control surface
  index.js       the public API
  spec.js        a mock written as a route file
  providers/     the mocks, one file per group of them
  ui/            everything a person sees: HTML, CSS, the panel
    templates/   the markup
    assets/      the styles

The engine knows nothing about HTML

src/harness.js does four things: it matches a request to a route, it records what it was asked, it keeps the state the mock decided on, and it answers over a control surface (/_control).

Everything a person sees — the control panel, the hosted checkout — lives in src/ui/ and is put on a mock by attachViews. The two are separated on purpose.

The engine works without the browser

new MockService('acme') is a perfectly good mock. It simply has no page until the browser layer is attached.

The page changes without the engine

The markup is in templates/, the styles in assets/, and the browser code is in the template itself.

Neither has to know about the other

The engine does not import the UI, and the UI does not import a provider.

A provider that wants a checkout declares it, rather than reaching into the browser layer: 

service.checkout = {
  title: 'Acme (mock)',
  find: (reference) => ({ reference, amount: '10.00', merchant: 'The shop' }),
  onDone: (reference, outcome) => recordIt(reference, outcome),
}

The UI mounts it; the engine never looks at it.

No dependencies

There are none — not at runtime, not in the tests, not in the lint. Node is the whole toolchain. This is not asceticism; it is the thing that makes the mocks easy to adopt.

  • A project can depend on the package without an install step of its own.
  • A contributor can add a mock without learning a framework.
  • The container image has nothing in it to install, so it stays small and starts instantly.

The lint is the clearest example. There is no eslint in it; scripts/lint.js parses every file with node --check and checks the house style — no semicolons, no trailing whitespace, a newline at the end. The footprint budget is the same idea: scripts/footprint.js measures the running mocks with node and ps.

The promise that is checked

The README says the mocks are light. A promise nobody checks is a promise that erodes, so it is a budget, and it fails the build. 

npm run footprint
  mocks       18 in one process
  memory      51 MB
  idle CPU    0.3%
  startup     432 ms

  budgets: memory <= 120 MB, startup <= 5000 ms, idle CPU <= 1%

The budgets are deliberately loose. They catch a regression that adds a runtime — a dependency, a poller, a timer that never stops — not a difference between two machines.

The categories

The mocks are grouped by what they stand in for, and the grouping is part of the API.

The compose file uses the same names as profiles, so --profile payments starts the payment mocks and nothing else. A project should not pay for eighteen containers to test one flow.

One process, many mocks

api-mock-services start stripe paystack flutterwave starts three servers in one process, on one port each. That is the difference between one container and three, and between 51MB and 153MB.

It also means the mocks share a fate: one SIGTERM stops all of them, and the ports are freed properly.

The control surface

/_control is the API the command line and the panel both drive.

RouteWhat it does
POST /_control/outcomeChoose how the next payment goes
POST /_control/failMake the next call fail — server, unauthorised, unavailable, timeout, network
POST /_control/webhookSet the webhook settings, and send it
POST /_control/resetForget everything
GET /_control/requestsEverything the mock was asked
GET /_control/logsThe requests, as they happen (SSE)

The panel is a view of it. The command line is a client of it. They cannot drift, because there is only one implementation.

The rules a mock keeps

The real shape

The paths, the fields and the status codes are the provider's, so the code under test does not change when it is pointed at a mock.

The state is kept

What the service was asked, and what it decided, is on service.state and service.requests.

The reference decides

A reference with success in it comes back successful, one with failed in it comes back failed — so a test can ask for either without a special flag.

No dependencies

Node's own server, so it runs anywhere.

Deliberate decisions, and why

Not DNS masquerading

Hijacking api.paystack.co needs a CA certificate installed, rights to change /etc/hosts, and it leaks real traffic for any domain the mock does not cover. The alternative is one line with no certificate and nothing to clean up: 

eval $(api-mock-services env)

Not a Go or Rust rewrite

A native binary would be lighter and start faster. It would also mean a build step, a toolchain, and a contributor who cannot simply add a mock. The memory is already 51MB for eighteen mocks, and it is measured. The shareability is worth more than the last 30MB.

Not schema-driven everywhere

A specification describes a shape; it does not describe a state machine. A payment that is created, then paid, then refunded cannot be expressed in a .yaml, so those mocks are written as code. For the services that are only read from, a route file is enough — and createSpecMock fills the placeholders in without a YAML parser and without a dependency.
