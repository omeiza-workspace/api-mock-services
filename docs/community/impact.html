Adding yourself

Open a pull request that adds a row to ADOPTERS.md. That is all — no form, no email, no account. A row looks like this: 

| Acme Ltd | The payment tests in our Laravel checkout | 2026 |

If you would like a logo next to your name, put an SVG in docs/logos/ — monochrome, about 32px tall — and link it.

If you use the mocks and would rather not be listed, that is completely fine. The list is for the people who want to be found.

How to help the project

The project is small, and the useful contributions are unglamorous. Here is what helps.

Star it

A star says the project is worth keeping an eye on. It is the cheapest thing to do and it helps somebody find it.

Use it in a project

Point a suite at the mocks and open a pull request adding yourself to the adopters list. A working example is worth more than a description of one.

Open an issue

Report something that does not do what it should. A mock that is wrong is worse than a mock that is missing, because a test will trust it.

Add a mock

The shape of a provider's API is in the provider's own documentation. Give the mock the routes it really has and the state it really keeps, register it in src/index.js with a port, a category and a description, and add a test.

Add a spec

A route file in contrib/ is enough for a service that is only read from. It is JSON, it needs no dependency, and it does not have to be reviewed as JavaScript.

Refresh a specification

The specifications the mocks are checked against are fetched from the providers' own repositories by a scheduled job. If one of them has moved, that is worth knowing.

The house rules are short: no new dependencies, the provider's real shapes, and a test that would fail without your change. The contributing guide has the rest, and the contributing folder has the route-file rules.
